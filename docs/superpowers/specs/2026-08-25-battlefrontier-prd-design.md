# BattleFrontier（ptcg-cn-battlefrontier）PRD v1.0

> 项目代号 **BattleFrontier（对战开拓区）**——宝可梦世界观中考验对战实力之地，与本项目"测试卡组强度与策略"的定位同构。
> 仓库：`Bingtuu/ptcg-cn-battlefrontier`（待定）；包名 `battlefrontier`；CLI `bfsim`。
> 本文档是 PRD 与架构设计的合一文档，经 2026-08-25 头脑风暴讨论逐节确认。

---

## 1. 背景与定位

[ptcg-cn-db](https://github.com/Bingtuu/ptcg-cn-db)（数据基建层）已完成：覆盖简中标准赛制全部合法卡牌的本地数据库、快照化合法性引擎、三赛区真实赛事卡组管线、可复算统计三指标（WUR/WR/WWS）与 matchup 对阵矩阵、29+3 效果意图标签层，并在 PRD FR-10 中预留了 sim 库骨架契约（模拟结果永远落独立库，主库只读）。

**本项目（BattleFrontier）是数据层之上的应用层**：构建宝可梦卡牌（PTCG 简中环境）完整规则模拟引擎与 AI 智能体，通过大规模模拟对局回答三类问题：

1. **强度**：卡组 A 对抗卡组 B 的胜率是多少？
2. **策略**：某卡组在某对阵下的最优策略是什么（以决策数据聚合报告形式产出）？
3. **敏感性**：调整卡组中某些卡牌（宝可梦、物品、支援者）是否对胜率有显著影响？以及探索新比赛标准环境（如 2026-09-16 30 周年卡包发售后的 J 标环境）下不同卡组和主轴的强度。

## 3. 目标与非目标

### 3.1 一期目标

- 规则引擎可完整模拟 PTCG 简中标准环境（G/H/I）真实对局，种子确定性
- 效果 DSL + 解释器可用，覆盖当前环境头部卡组（以 db 的 WUR 排名驱动选组）涉及的全部卡
- 通用启发式 Agent 可用，参数全暴露
- CLI 实验工具：提交实验 → 多进程执行 → 结果落库 → 结构化报告（胜率 + 置信区间 + 决策聚合 + 换卡敏感性）
- LLM 辅助 DSL 编写管线（试验性）并记录质量数据
- 模拟 matchup 与真实赛事 matchup 矩阵的偏差报告（校准基线）

### 3.2 非目标（一期明确不做）

- Web UI / 对局图形界面
- 裁判判罚、超时等赛事规则
- V-UNION 四部件机制
- MCTS / RL（一期只做接口预留与分层架构保证）
- 万局级以上规模的分布式调度
- 卡组构筑自动优化（遗传算法/搜索式组卡）

## 4. 总体架构

```
┌─────────────────────────────────────────────────┐
│  报告层   聚合统计 / 决策数据报告 / 对阵矩阵对比    │
├─────────────────────────────────────────────────┤
│  实验层   Runner（多进程、种子确定性、实验定义、    │
│           结果落独立 SQLite · 遵守 FR-10 契约）    │
├─────────────────────────────────────────────────┤
│  决策层   Agent 接口 ── 通用启发式 → MCTS（后续）  │
├─────────────────────────────────────────────────┤
│  引擎层   规则引擎：GameState / 阶段机 / 行动枚举 /│
│           隐藏信息与随机源                          │
├─────────────────────────────────────────────────┤
│  效果层   ★ 效果 DSL + 解释器（本项目核心差异点）  │
│           DSL 定义库（YAML，按卡编写，版本化）      │
├─────────────────────────────────────────────────┤
│  数据层   ptcgdb.sdk（open_db / open_jsonl）      │
│           卡牌数据 / 合法性 / 卡组 / effect_tags   │
└─────────────────────────────────────────────────┘
```

架构边界规则：

- **效果层与引擎层严格分离**：引擎只懂规则骨架（回合阶段、伤害计算、奖赏卡、胜负判定），"这张卡做什么"全部由 DSL 定义、解释器执行。引擎对卡牌内容零硬编码。
- **DSL 定义库是独立资产**：每张卡的 DSL 定义以卡 id / name_group 关联，进版本控制，可独立测试（单卡效果测试不依赖整局模拟）。
- **Agent 通过接口看局面**：引擎向 Agent 暴露"当前合法行动列表 + 可见信息视图"，Agent 返回选择的行动。该接口是启发式 / MCTS / RL 共用的。
- **数据只进不出**：消费 db 项目只读；模拟结果永远落本项目独立库（遵守 FR-10 骨架契约）。

## 5. 效果 DSL 设计（核心）

### 5.1 载体形态

结构化 YAML：每张卡一个 YAML 文件，效果是"原语节点树"，Pydantic schema 强校验（写错字段名、缺参数直接报错）。零解析器开发成本，对 Git diff 友好，天然是"数据"——未来可入库、可被工具生成。若将来嫌 YAML 啰嗦，可在其上叠加文本糖编译到同一 AST——**AST 是稳定中间层，载体可换**。

### 5.2 原语集

四类节点，全部对齐 db 项目 `config/vocabularies/effect_tags.yml` 的 29 意图标签 + 3 机制 flag（效果分类的现成事实源）：

- **动作原语**（原子操作）：`draw / search_deck / discard / damage / heal / attach_energy / switch / apply_status / flip_coin / mill / recover_from_discard / look_at_top …`，带类型化参数（对象选择器、数量、条件）
- **选择器**（作用对象）：`self / opponent_active / own_bench / chosen_pokemon / all_with_tag …`；选择是 PTCG 效果中最复杂的部分，独立成体系；运行时交互选择由 Agent 决策
- **条件/触发器**：`on_play / on_attack / ability_once_per_turn / when_damaged / if_stadium_in_play …`，区分主动发动与被动监听
- **成本与限制**：能量成本、丢弃成本、`once_per_turn`、前提条件（如需进化）

示意（"博士的研究"风格）：

```yaml
card: name_group=博士的研究
effects:
  - trigger: on_play
    cost: [{action: discard, selector: own_hand, count: all}]
    actions:
      - {action: draw, count: 7}
```

**招式绑定（task 012 补充）**：`trigger: on_attack` 的效果块须以 `attack: <招式名>` 字段绑定到
`CardDef.attacks` 中的具体招式；被绑定招式的伤害与附加效果全部由该效果块结算
（damage 原语负责伤害与目标，引擎只按规则骨架对战斗场目标结算弱点 ×2 / 抗性 -30，
备战区目标不计算——rules-manual §6），`AttackDef.damage` 仅作装载/展示数据；
未绑定的招式仍走引擎白板固定伤害路径。

### 5.3 覆盖策略：原语先行，逐卡落地

从真实卡组反向驱动：取当前 G/H/I 环境 WUR 前 N 套卡组 → 列出涉及全部卡 → 归并所需原语 → 原语实现一个、解锁一批卡。第一批原语只做到覆盖这批卡组为止（YAGNI），不为长尾冷僻效果提前设计。

### 5.4 可观测性设计（数据交互）

DSL 不只定义"效果怎么执行"，还定义"执行时留下什么数据"：

- **执行事件流**：解释器每执行一个原语节点发出结构化事件（`effect_id / card / trigger / 选择器结果 / 参数 / 结果`）。事件流是回放、人工 check、过程统计三者的共同数据源——一份数据三种消费。
- **DSL 内统计锚点**：效果定义可声明 `observe:` 标记（如"这次检索选择了哪张牌"标为关键决策点），报告层按锚点直接聚合，无需事后从原始事件打捞。
- **人工 check 模式**：Runner 支持单局逐步模式，事件流渲染为人类可读回合记录（"回合3：A 使用博士的研究，弃 3 抽 7"），用于规则正确性验收与 AI 决策质量抽查。

### 5.5 LLM 辅助编写管线（一期，试验性）

harness 全部固定为 skill + 严格 prompt：

- `dsl-authoring` skill：输入 = 卡的 `text_raw` + effect_tags + DSL schema 文档 + 编写规范；输出 = YAML 草稿
- **三道验收闸**：schema 校验 → 该卡单卡单元测试 → 人工核销，全过才入库
- 一期声明为试验：用它编写一期主流卡组的一部分卡，记录 LLM 一次通过率 / 人工修改量，作为二期是否批量铺开的决策依据

## 6. 规则引擎核心

### 6.1 GameState

不可变状态 + 事件溯源倾向。完整局面 = 双方手牌 / 牌库 / 弃牌堆 / 奖赏区 / 场上宝可梦（含进化链、附着能量、伤害指示物、特殊状态）+ 回合阶段 + 效果持续修饰器（如"本回合伤害+30"）。状态可序列化（快照 / 存档 / 并行分发依赖它）。

### 6.2 阶段机

PTCG 回合结构是显式状态机：抽牌阶段 → 准备阶段（进化 / 附着能量 / 物品 / 支援者 / 竞技场，自由序）→ 战斗阶段 → 回合结束检查，外加特殊检查点（开局布阵、奖赏卡拿取、昏厥对换、特殊状态判定）。状态机每步向当前 Agent 枚举**合法行动列表**，Agent 选一，引擎推进。"枚举合法行动"接口同时保证 AI 永不做出非法操作。

### 6.3 隐藏信息与随机源

- Agent 只拿到过滤后的可见视图（对手手牌数量可见、内容不可见）
- 所有随机（洗牌、掷币、抽牌）走单一可注入随机源，**种子决定一切**——同种子同局完全复现（硬验收项）
- 洗牌顺序在开局由种子确定：牌库内容对引擎确定、对 Agent 隐藏

### 6.4 规则正确性策略

规则骨架以**简中官方规则书 + 官方 Q&A** 为事实源，每条规则实现配单元测试并标注出处。争议规则（时序、连锁）进规则决议日志，不猜。

### 6.5 机制范围声明

- 只模拟游戏内规则，不含裁判判罚 / 超时等赛事规则
- **ACE SPEC 必须支持**：每卡组最多携带 1 张（卡组校验规则）+ 一期目标卡组涉及的 ACE SPEC 卡效果
- V-UNION 不实现；其他特殊机制（太晶 ex、超级进化 ex 等）按"一期目标卡组需要才做"原则逐个评估

### 6.6 训练家卡与 ACE SPEC 的骨架规划

训练家卡是"内容"不是"骨架"：效果全部走 DSL（M2 起经 `play_trainer` 行动接入解释器，`on_play` 触发器），引擎只实现使用规则：

- **物品**：每回合不限次数
- **支援者**：每回合限 1 张（`supporter_played_this_turn` 回合标记，与 `energy_attached_this_turn` 同构）+ 先攻方第一回合不可用
- **竞技场**：每回合限 1 张；不得与场上同名；打出新场时旧场进弃牌堆（顶替）；持续/触发效果经 DSL `if_stadium_in_play` 类条件触发器，由解释器按场上状态判定
- **道具**：每只宝可梦限挂 1 个（`InPlayPokemon.attached_tool` 槽位），随昏厥一并弃置
- **ACE SPEC**：两层——①"每卡组限 1 张"属构筑校验层（对齐 db `validate_deck`，实验加载卡组时校验）；②局内为普通物品/道具/特殊能量 + DSL 效果，引擎无特殊分支

**规则事实源文档**：`docs/rules-reference.md`——官方规则系统梳理（术语统一为官方用词，如「昏厥」）、每条规则的引擎落点与核对状态、规则决议日志（附录 A）。规则引擎实现与 `dsl-authoring` harness 的 prompt 均以它为准。

## 7. 决策层（Agent）

### 7.1 接口

`observe(visible_state, legal_actions) -> action`；双方 Agent 可为不同实现/参数（支持"强 Agent vs 弱 Agent"对照实验）。

### 7.2 通用启发式（一期）

- **局面评估函数**：奖赏差、场面战力、手牌质量、能量就绪度、牌库资源等线性/规则加权
- **决策规则**：开局布阵优先级、每回合行动排序（特性 → 进化 → 能量 → 物品 → 支援者 → 攻击选择）、斩杀检测
- 参数全部暴露在实验定义里——"某参数扰动对胜率的影响"本身就是换卡敏感性之外的另一类实验
- 不做单卡组定制逻辑（D10）

### 7.3 MCTS 预留

- 引擎支持状态快照与快进模拟（rollout）
- 隐藏信息处理采用 determinization（对对手手牌/牌库采样假设世界）
- 一期不实现，仅保证架构不挡路

## 8. 实验层（Runner 与结果存储）

### 8.1 实验定义

实验即一份 YAML：卡组 A / B 定义（从 db 拉真实赛事卡组，或本地 decklist 文件）、局数 N、种子起始值、Agent 配置、环境快照日期。**可复现 = 实验定义 + 代码版本 + 数据版本三者锁定。**

### 8.2 执行

单机多进程 worker 池。局与局天然独立，按种子分片并行；主进程收集结果增量落库。一场 2,000 局实验目标分钟级完成（一期性能基线实现后实测记录）。

### 8.3 结果库（独立 SQLite，遵守 FR-10 契约）

三层表：

- `experiments`：实验定义快照 + 代码/数据版本 + 状态
- `games`：每局元数据——胜负、回合数、先后手、种子、双方卡组 id
- `game_events`：单局完整事件流（执行事件 + 决策锚点），供回放与聚合

关联主库经 card_id / name_group / 快照 id；主库只读。

### 8.4 确定性

同实验定义 + 同种子区间重跑，`games` 层结果逐局一致（硬验收项）。

## 9. 报告层（统计口径）

- **胜率报告**：A vs B 胜率 + Wilson 95% 置信区间、先后手拆分、平均回合数、平局率；2,000 局下 CI ≈ ±2.2%
- **决策聚合报告**：按 DSL 统计锚点聚合——关键决策点的选择分布与各自胜率（如"首回合检索选了哪张牌" × 最终胜率）
- **换卡敏感性**：实验定义原生支持对照组/实验组模式，一次提交多组实验，报告并排呈现 ΔWR + 置信区间 + 显著性检验
- **元环境对比**：模拟 matchup 矩阵 vs db 真实赛事 matchup 矩阵偏差表（校准目标，不设死阈值）
- 所有报告 meta 回显：实验 id、种子区间、代码/数据版本、局数——数字可原样重放（与 db 项目"可复算"哲学一致）

## 10. 测试与验收策略

### 10.1 硬验收（必须通过）

- **规则正确性**：规则骨架每条规则有单元测试并标注官方出处；DSL 覆盖的每张卡有单卡效果测试；关键对局场景（开局、昏厥对换、特殊状态结算）有集成测试
- **确定性**：同种子重放逐局一致；多进程并行与串行结果一致
- **数据契约**：结果库 schema 符合 FR-10 骨架；主库全程只读（以只读连接强制）

### 10.2 校准目标（持续迭代，不设死阈值）

- 模拟 matchup 矩阵 vs db 真实赛事 matchup 矩阵偏差表定期产出，作为启发式 Agent 与规则实现的迭代依据

### 10.3 试验性验收（LLM 管线）

- 记录 LLM DSL 草稿一次通过率、人工修改量；一期末给出"二期是否批量铺开"的决策建议
